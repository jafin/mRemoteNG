# Tasks

Depends on `add-connection-file-key-slots`, which introduces the rekey. Task 3.1 exists because of
it, and getting 3.1 wrong writes a file whose contents are encrypted under two different keys.

Do not start before it ships.

## 1. Hold ciphertext until something asks

- [x] 1.1 Give the record a pending-secret slot beside each `SecureString`: the ciphertext, and whatever resolves it. Populated by the deserializer instead of assigning a decrypted value. — `PendingConnectionSecret`, one beside each of `_password`, `_rdGatewayPassword`, `_vncProxyPassword` and — not asked for, but the deserializer defers it too and leaving it eager would have kept the old code path alive for one field — `ContainerInfo._containerPassword`. The resolver and the key are shared by every secret in one load rather than built per field.
- [x] 1.2 Decrypt on first read, from **both** the plain-text property and the `SecureString` accessor, and cache into the existing field. Two doors to one secret and only one of them lazy would give different answers depending on which a caller used — the defect `narrow-connection-password-exposure` §2.4 tests against. — Both doors end at `OwnSecret`. They still differ in what they consult first, exactly as before: the `SecureString` accessor takes a bound credential record without a plain-text copy, and both then ask the resolved property. **The record's own value is reached last**, which is what makes deferring worth anything — a connection inheriting or borrowing its password never decrypts its own stored one at all.
- [x] 1.3 Resolve exactly once under concurrent reads. The tree is read from the UI thread and from the host-status monitor, and two threads decrypting the same record must not produce two `SecureString`s of which one is silently dropped and never disposed. — One `Lock` per record, covering all three secrets: the only contention that exists is two threads on one record, and past the first read it is uncontended. Notifications are raised outside it, since a `PropertyChanged` handler runs the tree, the property grid and the auto-saver, none of which belongs inside a lock a getter also takes.
- [x] 1.4 Assigning a secret discards the pending ciphertext. Otherwise a record edited before its first read would decrypt over the top of the user's new value on the next read. — Discarded *before* the "did the value actually change" comparison and unconditionally, because the comparison is against the decrypted field, which is empty precisely when the pending value is the one that matters.
- [x] 1.5 Do not defer what the load already needs. The root sentinel is decrypted to validate the key, and that must keep happening at load — it is what turns "wrong key" into one honest failure instead of one per connection. — Untouched. So is the full-file-encryption decrypt, which produces the XML the nodes are read from and cannot be deferred by definition.

## 2. Failure has to stay legible

- [x] 2.1 A secret that fails to decrypt raises the failure to the user against **that connection**, and never resolves to an empty string. Several callers read empty as "no password configured" and fall through to the configured default password — a lazy failure that returns empty would send the wrong credentials to a host rather than reporting anything. — `ConnectionSecretDecryptionException`, carrying the connection's name and which secret it was, reported to the message collector with `logOnly: false` so it reaches the user rather than only the log. A failed resolve deliberately **leaves the pending value in place**: clearing it would make the next read answer empty, which is the outcome this exists to prevent.
- [x] 2.2 Report a failed decrypt once per record, not once per read. The property grid re-reads constantly; a failure per repaint is a wall of dialogs over one broken field. — The failure is remembered on the pending secret, so it is once per secret per record rather than once per record. **The decryption is attempted once too**, which review caught: the record keeps a secret that failed so a later read cannot answer empty, which means every later read comes back here, and a wrong key does not become the right key by being tried again — it just costs another full derivation on whichever thread asked. The exception is still thrown every time, which is what stops a caller quietly carrying on, and a fresh one is built each time so every caller gets a stack trace of its own read.
- [x] 2.3 Keep the load-time key check as the first line. 1.5 is what makes 2.1 rare: a wrong key should still be caught at load, and 2.1 exists for the single corrupt attribute in an otherwise good file.
- [x] 2.4 Tests: a corrupt attribute fails against its own connection and leaves every other connection openable; the failure is reported once; nothing resolves to empty. — All three, plus the other half: a store whose sentinel does not decrypt fails while it is being opened and not with a per-connection error, which is the assertion that fails if 1.5 is ever undone.

## 3. Saving

- [x] 3.1 **A save that changes the key must decrypt everything first.** Rekey, master-password change and hardening a classic store all re-encrypt the contents; a record still holding old-key ciphertext that is passed through unchanged produces a file encrypted under two keys, and the half under the old key is unrecoverable. Force a full `DecryptBatch` on those paths and treat any failure as a refusal to save, not as a field to skip. This is the one destructive outcome in this change. — Done in two layers, and **not** by asking each save path to declare itself. `ConnectionSecretKeyIdentity` describes the key by value — provider kind, engine, mode, iterations, PRF, the file key by reference, the password by fingerprint — and the pass-through applies only when the identity the write encrypts under equals the one the bytes were read under. A key change therefore disables it on its own, with nobody having to remember, and the secrets are decrypted and re-encrypted normally; a failure throws and refuses the write. **The rekey needed more than that**: `ConnectionFileRekey.Apply` disposes the old key, so by the time the save runs there is nothing left to decrypt with. It now decrypts the whole store *before* replacing anything, which also means an unreadable secret refuses the rekey while the store is still exactly as it was. **`DecryptBatch` is deleted, against the proposal's instruction to keep it**, because the reason for keeping it turned out not to hold. It was fast not because it ran across cores but because one provider instance decrypted many fields, and the AEAD provider caches the key it derived against the salt it derived it from — every field of a file this application writes shares one salt. The resolver keeps one provider for the same reason, so a forced full decryption now costs one derivation rather than one per record, and there is nothing left for a parallel batch to save. Deleting it was the honest move: it had no callers, and a bulk path kept "in case" is a bulk path nobody maintains.
- [x] 3.2 An ordinary save may write back the ciphertext of a record that was never read. Same key, same bytes, nothing to gain by decrypting them. — Two further conditions beyond the key matching, both load-bearing: nothing has assigned the secret since (there is no pending value left if it has), and the property would answer from this record rather than from a credential record, a linked connection or a parent folder. Without the second, saving a connection bound to a credential record would write its own stale bytes in place of the credential's password. The second condition resolves through the tree and the credential catalogue, so it cannot run under the record's lock — which leaves a window in which an edit lands, and the pending value is therefore **asked for again under the lock before the ciphertext is returned**. Review caught that; without it a save racing a user's keystroke could put the superseded password back in the file.
- [x] 3.3 Confirm 3.2 against the AEAD path specifically: passing ciphertext through unchanged means the nonce is not regenerated for that field. That is correct — the plaintext did not change either, so it is the same message under the same key, not nonce reuse across different plaintexts. Record the reasoning where the pass-through is written; a reader who spots "reused nonce" and not "identical message" will otherwise fix a bug that is not there. — Recorded on `AbstractConnectionRecord.TryGetStoredCipherText`, which is where a reader meets it.
- [x] 3.4 Export writes a classic copy at a different level and re-encrypts everything, so it is a key change by 3.1's definition. Confirm it takes that path. — It does, and by construction rather than by inspection: the key identity is an **optional** constructor argument on the node serializer, and every caller that builds one by hand — the export path is the only one — passes nothing and gets full re-encryption. Pinned by a test, because "the safe default" is only safe while it stays the default.
- [x] 3.5 Tests: a rekey forces decryption and the file afterwards decrypts wholly under the new key; an ordinary save of an untouched store leaves the secret bytes identical; a save after editing one connection rewrites that one and passes the rest through. — Eight, in `ConnectionSecretPassThroughTests`, all through the real saver and deserializer against a file on disk. Beyond the three asked for: a rekey that meets an unreadable secret is refused and leaves the key, the protection and the file byte-identical; a save under a changed key that cannot read a secret is refused; hardening a classic store re-encrypts secrets nothing ever read; and the untouched-store test also asserts the save did not decrypt anything, since writing identical bytes would look the same either way.

## 4. Consumers

- [x] 4.1 Audit every reader of `Password`, `RDGatewayPassword` and `VNCProxyPassword` for one that cannot tolerate a first read doing work — anything holding a lock, on a paint path, or inside a `catch`. — Eighty-eight reads across the product. Three files both read a secret and take a lock — `SqlConnectionsSaver`, `PuttyBase`, the VNC protocol — and in all three the two are in unrelated methods; no secret is read inside a lock. The connect path reads through `ConnectionInitiator.OpenConnection`, whose whole body is already inside a `try`/`catch` that reports to the message collector, so a failure there reports and does not open the connection, which is the intended behaviour rather than a hazard. Nothing reads a secret from a paint handler.
- [x] 4.2 `CredentialImportHelper.HasPassword` asks whether a secret exists for every node in a file being imported. Under this change that question decrypts the whole file one record at a time, which is worse than the batch it replaced. Answer it from the pending ciphertext's presence instead. — **Done as far as it can honestly be, and the task's premise is wrong in a way worth recording.** Presence of ciphertext does not answer the question: an empty password is written as the encryption of an empty string, not as an empty attribute — deliberately, so the file does not disclose which connections have no password — so *every* connection in a store carries a `Password` ciphertext and answering from presence would report that every node has credentials. What `ConnectionInfo.HasPassword` does instead is answer immediately where it certainly can (nothing stored, no parent, no linked connection, no credential record) and decrypt only otherwise, and `HasCredentials` now asks it **last**, after the two string comparisons that can answer for free. Making presence sufficient would mean writing empty passwords as empty attributes, which trades a real disclosure for a startup cost, and was refused.
  **Both walkers also isolate the failure per node**, which review caught: `HasCredentials` recurses over every node in the file, so one damaged password would otherwise abort the scan and make the whole import report that there is nothing to extract. An unreadable secret counts as a secret. `ExtractCredentials` goes further and skips that node altogether rather than extracting an empty credential — it ends by clearing the connection's own password, and doing that after failing to read it would lose the secret outright.
- [x] 4.3 Confirm the property grid does not decrypt a secret merely by displaying the row. It renders `PasswordPropertyText`, so it should not need the value — if it does, selecting a folder would decrypt every child. — It does read the value: `PasswordPropertyText` masks what the getter returned rather than replacing the call. So selecting a connection decrypts that connection's password, and selecting several decrypts each of them. The hazard the task names does not arise, though: the grid binds to the selected objects only, and a folder's `Password` is its own field — selecting a folder decrypts nothing belonging to its children.
- [x] 4.4 Tests: reading a secret from two threads decrypts once; a record whose secret is never read never decrypts; importing a file does not decrypt it. — First two as asked, with the second stated twice: nothing in a freshly opened file is decrypted, and reading one connection's password leaves the others untouched. The third is narrowed to what 4.2 makes true — a record with nothing stored is answered without decrypting — since a file whose connections have passwords must decrypt them to answer whether they do.

## 5. Verification

- [x] 5.1 Full build; zero new analyzer warnings. — Clean. Built to a temporary output path because a running mRemoteNG.exe holds `bin\`; the compile is unaffected by that and the three pre-existing warnings in the test project (`CA1050`, `MA0047`, `CA1859`) are untouched by this change.
- [x] 5.2 Full test suite; zero failures, no `[Ignore]`. — See the commit message for the count. `ConnectionSecretDecryptionTimingTests` was rewritten rather than deleted: it was written to characterise eager decryption and to fail the day it changed, and this is that day, so each of its assertions is now the opposite claim about the same thing.
- [x] 5.3 `openspec validate decrypt-connection-secrets-on-demand --strict`.
- [x] 5.4 Measure the startup claim rather than asserting it. Open a file of ~200 connections before and after; report the number. The proposal says this *should* be faster because the batch is skipped, and a proposal that guessed wrong about this file's behaviour once already should not guess twice. — **Measured, and the claim holds.** A classic store of 200 connections at 600,000 PBKDF2 iterations: opening it takes **305–308 ms** now, against **918–1009 ms** before — the batch that used to run at load cost 620–711 ms and no longer runs.

  The first measurement of this was worse and was wrong, which is worth recording because the cause is the same one the proposal got wrong about the batch. Resolving each secret through a provider built for that one call made every read a full derivation, **234–242 ms**, and the number looked like an unavoidable consequence of deferring. It was not: the AEAD provider caches the key it derived against the salt it derived it from, every field of a file this application writes shares one salt, and building a provider per read threw that away. That is also what the batch was really buying — one provider across many fields, not the parallel fan-out. Keeping one provider behind a lock restores it.

  As measured now: opening the file **305 ms**, the first password read **238–242 ms** — one derivation, once — and the remaining 199 **8 ms between them**. So opening a file is three times faster, the first connection of a session costs a fifth of a second more, every connection after it is free, and 197 passwords stay out of the process until asked for. On a hardened per-file-key store there is no derivation at all and even the first read is free.

- [ ] 5.6 Manual: rekey a store with connections that were never opened in that session, then reopen the file and connect to one of them. This is risk 1, and it is the check that a green suite cannot make convincing.
- [ ] 5.7 Manual: open a file, connect to one connection, save, and confirm the other connections' stored secrets are byte-identical to what they were.
