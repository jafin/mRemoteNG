# Tasks

**This proposal is split across releases.** Section 1 ships a release ahead of the rest; sections 2
onward wait for `add-storage-format-opt-in`. See
[SECURITY-AUDIT-3416.md](../SECURITY-AUDIT-3416.md) for the full order.

## 1. Version refusal — ships first

- [x] 1.1 In `SqlDatabaseVersionVerifier`, treat a database version newer than the build as a refusal that names both versions, instead of proceeding to read rows. — Two defects, not one. The verifier did already return false, but reported it as a generic incompatibility warning; it now reports the newer case at error severity naming the database version, the product and the highest supported version (`ErrorDatabaseVersionNewerThanClient`). **`SqlConnectionsLoader` was discarding the result entirely** and reading rows regardless, so the check existed and changed nothing.
- [x] 1.2 Tests: a newer version loads nothing and reports both numbers; the current version still loads; an older version still loads. — `SqlDatabaseVersionVerifierTests` plus two `SqlConnectionsLoaderIntegrationTests` cases, one asserting the rows are never read.
- [x] 1.3 Release this ahead of the rest. Until every client refuses a newer database, upgrading one produces silent garbage on the others rather than a message — see design.md, "Refuse a database newer than the build".

**Scope note.** `IsNewerThanSupported` was added to `ISqlDatabaseVersionVerifier` rather than making
the loader honour `VerifyDatabaseVersion` outright. The two failure modes need opposite handling: a
database too old to upgrade also returns false, and refusing those would lock out installations that
work today. Only the newer case is refused.

## 2. Provider selection

- [x] 2.1 Add a version constant for authenticated encryption and a helper that returns the provider for a given `ConfVersion`, mirroring `CryptoProviderFactoryFromXml`'s role on the XML side. — `CryptoProviderFactoryFromSqlVersion`, with `AuthenticatedEncryptionVersion` at 3.6. A null version reads as legacy, and the asymmetry is the reason: reading legacy ciphertext with the AEAD provider fails cleanly because GCM authenticates, while the reverse does not fail at all — AES-CBC has no tag, so it yields plausible nonsense rather than an error. (Task 6.6 later measured what an older client does with an upgraded database, and it never reaches the rows: the sentinel is AEAD too and is read first. The asymmetry still decides the null case, but the consequence is a password prompt that cannot be satisfied, not connections with empty passwords.)
- [x] 2.2 Replace the hardcoded `new LegacyRijndaelCryptographyProvider()` in `ConnectionsService.cs:309` with the helper, fed by the metadata the loader already retrieves. — **The loader could not be given a provider at all.** It learns the version inside `Load()`, after the metadata is read, so the constructor now takes the *rule* — `Func<Version?, ICryptographyProvider>` — rather than a provider chosen before anything is known. One provider then serves both the sentinel and the rows, because they are encrypted together and a mismatch would authenticate a password that decrypts nothing.
- [x] 2.3 Replace the hardcoded provider in `SqlConnectionsSaver.cs:153` the same way. — The saver already retrieves the metadata, so the version was to hand.
- [x] 2.4 Check `SqlDatabaseMetaDataRetriever.cs:96`, which builds its own legacy provider, and route it through the helper or document why its use is version-independent. — Routed, and it is the **most** important field to route, not an afterthought. `Protected` is a fixed, published plaintext encrypted under the master password: at the legacy provider's unsalted MD5 derivation it is an ideal offline cracking oracle, testable at GPU speed by anyone with read access to `tblRoot`. Leaving it legacy while moving the rows to AEAD would preserve the cheapest attack on the whole database, and would also break the load, which reads both with one provider.
- [x] 2.5 Tests: the helper returns legacy below the version and AEAD at or above it; the loader and saver agree for a given version. — Ten cases in `CryptoProviderFactoryFromSqlVersionTests`, including that each call gets its own provider instance (the AEAD provider caches derived keys in fields, so sharing one across the saver and a batch decrypt would give intermittent wrong answers rather than a clean failure) and that the schema version and the AEAD version never coincide, which is what stops a newly created database silently choosing the format upstream mRemoteNG cannot read.

**Two defects found while wiring this, both outside what §2 asked for.**

`WriteDatabaseMetaData` wrote `ConnectionsFileInfo.ConnectionFileVersion` — the XML file-format
constant, **3.2** — into `tblRoot.ConfVersion` on every save. So a 3.5 database was stamped back to
3.2 by each save and the next load re-ran the 3.2→3.5 schema upgraders to put it back. Survivable
churn while nothing depended on the number; fatal once the number decides how secrets are encrypted,
because an upgraded database would be marked 3.2 by the first ordinary save while its rows were
written as AEAD — the half-migrated state design.md exists to make impossible, reached without anyone
doing anything wrong. It now preserves the database's own version.

`SqlDatabaseVersionVerifier` accepted exactly one version. Two are readable now — 3.5 and 3.6 share a
schema and differ only in encryption — so the check is a range. An equality against the new highest
version would have reported every database in the field as unsupported.

## 3. Refuse to write a legacy database

- [x] 3.1 ~~Make `SqlConnectionsSaver` refuse when the database is below the new version~~ — **task rewritten after implementing it.** The saver now warns once per database and saves anyway. Refusing was a bigger hammer than this change's own reasoning called for: design.md establishes that the *upgrade* must not be prompted, because it decides for a whole team and is irreversible — which says nothing about whether a legacy database should keep accepting writes. Refusing improves nothing today (the weak encryption is the state these databases are already in), stops work until an administrator acts, and because saves are automatic and debounced it lands on an ordinary rename. It also contradicted this fork's own precedent, where a classic connection file stays fully writable and hardening is offered rather than imposed. `WarnOnceIfTheDatabaseStillStoresSecretsWeakly`, keyed on server and database name so two stores on one server are warned about separately.
- [x] 3.2 Confirm the refusal surfaces where a user will see it rather than only in the log — a save that silently does nothing is worse than the weak encryption it avoids. — Moot in its original form, since nothing is refused, but the concern behind it decided the shape of the warning. It goes to the message channel and **never to a modal**: a save can run on the debounce timer rather than on the user's action, so a dialog could appear over unrelated work or off the UI thread. The text says the change *was* saved — it must not read as a failure — names **File → Options → SQL Server**, and states what upgrading costs: older builds and other mRemoteNG installations stop being able to open the database. That last part is the piece nobody can find out for themselves before acting.
- [x] 3.3 Tests: a save against a legacy database does not write and reports; a save against an upgraded database writes AEAD ciphertext. — **Restated by the change above, then done against a real SQL Server.** The first half is now "a legacy database is still written, and its secrets stay legacy" — refusing improved nothing and stopped people working. Five tests in `SqlSaverEncryptionIntegrationTests`, which are the only ones in this change that can answer what is actually *in* the column afterwards: a saver and a loader that disagree produce a database nothing reads back, and testing either end alone would never show it. Also pinned: the two formats are not interchangeable, so "it decrypts with the legacy provider" asserts something; the warning is raised once and not on the second and third save; and an upgraded database is not warned about at all.

  Two things had to be got right to drive the saver, both recorded in the fixture because neither failure resembles its cause. `SqlConnectionsSaver` builds its own connector from `DatabaseConnectorFromSettings()`, so the tests set the application's SQL settings and put them back — a seam worth adding if that file grows. The settings password must be stored **protected**: `SettingsSecretProtector`'s no-marker fallback legacy-*decrypts* rather than passing a value through, so a plain password fails inside the save as "not a valid Base-64 string". And `SQLAuthType` must be set explicitly, or the factory discards the credentials for integrated security and builds a DataSource with the colon and port still in it, which SqlClient answers thirty seconds later with "the server was not found" — about a container that is running perfectly.

**The cost of this decision, recorded so it is not lost:** a team that never opens the SQL options
page keeps the weak format indefinitely. Refusing writes would have forced the issue. What replaces
that pressure is the options page's status line, which reaches the person who can actually decide —
and the warning, which at least means nobody can say they were not told.

**§3 also invalidates a decision recorded in §2, and the note there has been corrected rather than
left to be discovered.** §2 said a new database is created at the schema version, reasoning from the
connection file: write the older format so upstream mRemoteNG can still read it. Nothing reads a
database this build has only just created, so there is nobody to stay compatible with and no reason
to start it weak; new databases are created at the authenticated version. An *existing* database is
still never upgraded except deliberately, which is the part of the original reasoning that survives.

## 4. Upgrade

- [x] 4.1 Put the upgrade in the SQL options page and **do not prompt for it** when a database is opened — decided, see design.md. Deliberately not the once-per-store offer `add-storage-format-opt-in` defines: that suits the connection file, where the person prompted is the person affected. Here the decision is team-wide and belongs to whoever administers the database. — `SqlDatabaseEncryptionUpgradePrompt`, on the seam pattern `ConnectionFileRekeyPrompt` established, plus a status line and an **Upgrade Encryption...** button on the SQL Server page. Two decisions in the wiring are worth more than the wiring itself. The button appears **only when the connected database says it has something to upgrade**, because an always-visible button offering an irreversible team-wide change is an invitation to press it and find out what it does. And the status refreshes **only after Apply, never after Test Connection**: that button works on whatever is currently typed into the page, which may be a different server entirely, and a status line describing one database beside a button that upgrades another is how this lands on the wrong one.
- [x] 4.2 Authenticate the master password against the `Protected` metadata before touching a row. — By the sentinel's *contents*, not merely by decrypting without error. The legacy provider is AES-CBC with no authentication tag, so it does not refuse a wrong key — it returns rubbish. Without this check an upgrade with the wrong password would decrypt every secret to rubbish and write that rubbish back under the new format, destroying the database with no error raised at any point.
- [x] 4.3 Read every secret column with the legacy provider, rewrite with AEAD, raise `ConfVersion`, all in one `DbTransaction`. — `SqlDatabaseEncryptionUpgrade.Apply`. The version marker is raised **last and inside the same transaction**: it tells every future reader which provider to use, so it must not be ahead of the contents nor behind them. An empty column stays empty rather than becoming an encrypted empty string. Rows are read to completion before any update rather than updating through an open reader, so this does not depend on `MultipleActiveResultSets` being in the connection string for correctness.
- [x] 4.4 Warn before proceeding and require confirmation. Name upstream mRemoteNG among the clients that will stop reading the database, and say that this decides for colleagues who never installed this fork — see `add-storage-format-opt-in`. — Four paragraphs, ordered by what somebody needs in order to answer: what it fixes, who it breaks, and that a backup is the only way back. `BuildExplanation` assembles them outside the dialog so a test can assert what a security warning says without needing a window, and the test asserts the **words** — "mRemoteNG", "colleagues", "cannot be undone", "Back the database up" — rather than the resource keys, because a rewording that drops any of them is the regression worth catching. Two facts here are ones nobody can discover for themselves before acting: that the change reaches people who never installed this fork, and that mRemoteNG cannot walk it back.

  **Not tested end to end through the prompt, deliberately.** The refusal paths run against substitutes — a test that needed a SQL Server to find out that the user said no would not be run often enough to catch a regression on the path where they said no — and `Apply` is tested against a real database. Driving the whole prompt through the container as well would re-prove `Apply` while mutating static seams from a second fixture, and the seams are what the substitute tests depend on.
- [x] 4.5 Tests: a successful upgrade re-encrypts every secret and raises the version; a failure mid-way rolls back to a fully legacy database; a wrong password modifies nothing. — Eight, against a real SQL Server, because the transaction *is* the mechanism and a substitute cannot show it. **One of them found a real defect:** the rewritten sentinel was being encrypted with the root node's default password rather than the master password the upgrade had just authenticated, so an upgraded protected database would have refused the password it was upgraded with. That would have arrived in the field as a database nobody could open.

  A fifth question fell out of the wiring and got its own four tests: **must the upgrade ask for a master password at all?** It cannot be answered by looking at whether `Protected` is populated — it never is empty in a real database, since an unprotected store holds "ThisIsNotProtected" encrypted under the built-in default key. `RequiresMasterPassword` tries that key and reads what comes back, so a database with no master password does not put a password box in front of somebody who has never had one to type. A wrong answer is harmless: `Apply` authenticates whatever it is handed and refuses on its own.

  Two of the cases were written wrong first and are worth recording. "A wrong password modifies nothing" needs a database that *has* a master password: seeded unprotected, the store opens on the built-in default key and the supplied password is correctly ignored — the test was wrong, not the code. And the row insert is built from `INFORMATION_SCHEMA` rather than written out, because `tblCons` has dozens of NOT NULL columns and gains more as the schema rises; a hand-written INSERT goes stale as a failure about a column name, in a test about encryption.

## 5. Serializers

- [x] 5.1 Confirm `DataTableSerializer` and `DataTableDeserializer` are provider-agnostic — they take `ICryptographyProvider`, so this should be a check rather than a change. — Both take the provider through their primary constructor and never name one, so the check passes. **The check did not pass on what a failed decryption means, and that is a real defect this section found rather than a tidy-up.** `DataTableDeserializer.DecryptValue` caught `EncryptionException` and returned the ciphertext, commented "value may not be encrypted". Correct for the legacy provider, which cannot tell an altered value from one that was never encrypted — databases old enough to hold plain values exist, and refusing them would help nobody. Under AEAD it is exactly backwards: the tag fires precisely because the value *was* altered or written under another key, and passing it through hands the connection its own base64 as a password while the tamper detection reports nothing. That is the whole benefit of authenticating the ciphertext, discarded silently, and it is what task 6.7 exists to catch by hand.

  Fixed with `ICryptographyProvider.DetectsTampering`, defaulting to false and true on the AEAD provider — a capability the decision actually depends on, rather than a type test on a class name. A provider that detects tampering now reports the failure and yields an empty value: not an aborted load, because one altered row must not deny access to every other connection in the database, and a visibly missing password with a message naming the cause is something a person can act on. `FormatException` is caught alongside, because the authenticated provider reads the base64 before the cipher sees it, so text mangled badly enough failed *there* and escaped to kill the entire load.

- [x] 5.2 Check the commented-out block at `DataTableSerializer.cs:670-672` against the live code at `:673-675`; if it is a stale `SecureString` variant, remove it rather than leaving two versions of the comparison. — It was, and so was the matching pair at `:735-736`; both removed. What replaces the first is worth more than its deletion: that comparison is the "has this row changed" check, and it is **false for every connection that has a password, under either provider** — both generate fresh randomness per encryption (a random IV in the legacy provider, a random GCM nonce in the authenticated one), so encrypting the same password twice never yields the same ciphertext. Rows with a password are therefore always rewritten. Wasteful rather than wrong, it predates this change, and comparing plaintext instead would mean decrypting every stored row on every save to decide whether to write it — so it is recorded where the next reader will find it rather than fixed here.
- [x] 5.3 Tests: round-trip every secret column through both providers. — Nine in `SqlSecretColumnRoundTripTests`, over both providers. Three pin the behaviour the section is about: an altered value comes back empty and reported rather than as its own ciphertext; a never-encrypted value is refused under AEAD; and the same value is still read under the legacy provider, which is the compatibility that must survive. Two more keep the round-trip honest — no secret column is written in the clear (or a provider that encrypted nothing would pass), and the two formats do not read each other (or choosing the provider by version would be decoration). The last asserts the **list of secret columns against the live schema**, so a fourth one added later cannot go silently untested through both providers with the suite still green.

## 6. Verification

- [x] 6.1 Full build; zero new analyzer warnings. — Clean. Two `CA1859` warnings introduced by §4's test helpers were fixed rather than left, so the tree is back to the warning set it had before this change.
- [x] 6.2 Full test suite; zero failures, no `[Ignore]`. — 4,312 passed, 0 failed, including the SQL integration group against a real SQL Server in Docker. 31 of those tests are new in this change.
- [x] 6.3 `openspec validate encrypt-sql-backend-with-aead --strict`. — Valid.

**The four manual checks below are for the user, and three of them are now narrower than when they were written** — the automated coverage that arrived with §3, §4 and §5 has taken most of each. What is left is what a test genuinely cannot answer.

- [x] 6.4 Manual, against a real SQL Server: load a legacy database, confirm connections decrypt and a save is refused. — **Restated: a save is no longer refused, it warns** (see 3.1). Passed against a 3.5 database in a container: both connections loaded, their passwords decrypted, the save went through and the warning appeared once.

  **And it caught a user-facing defect no test could have.** The warning told the user to open **Tools → Options → SQL Server**. There is no Tools → Options — the Options item lives under **File**, and has done for long enough that the field behind it is still called `_mMenToolsOptions`, which is presumably how the wrong path spread. A warning whose entire purpose is to send somebody to a page they would not otherwise find, naming a menu that does not exist, is worse than no warning: it costs the reader their confidence in the rest of the sentence. Corrected in `WarningDatabaseNotUpgradedForEncryption` and in the eight documentation pages carrying the same path, six of which predate this change. Historical CHANGELOG entries were left alone — they describe releases where it may well have been true.

  This is the argument for doing the manual checks at all, in one line: every automated test in §3 asserts on the *substance* of that warning (`"weak encryption"`, raised once, not on the second save) and every one of them passes against a message pointing into thin air.
- [x] 6.5 Manual: upgrade it, confirm connections still decrypt, confirm the stored ciphertext changed shape, confirm a save now succeeds. — The upgrade itself is covered end to end by `SqlDatabaseEncryptionUpgradeTests` against a real database, including the sentinel moving with the rows. What is left is the path through the options page: that the status line appears after **Apply**, that the button appears only for a legacy database, and that the confirmation is legible at the size the dialog gives it. **Passed by hand.** The status line appears after **Apply**, the button appears only for a legacy database — the upgraded `mrng66` shows the status with no button — and the confirmation reads at the size the dialog gives it. Four defects on this path were found by hand and none of them by a test: the status only refreshed in the Apply tail, the row drifted off the page at 150% scaling, the warning named a menu that does not exist, and a tamper failure did not say which connection it was. That is the argument for the manual pass, not against it.
- [x] 6.6 Manual: point a build from before task 1 at the upgraded database and record what it does. This is the failure the whole sequencing exists to prevent, and it is worth seeing once. — **Done, and it falsified the prediction this proposal was written on.** Method: the pinned SQL Server image in a container on a fixed port; a database seeded at 3.5 through the real saver and upgraded through `SqlDatabaseEncryptionUpgrade.Apply`; then a build of `a921eef2e` — the commit before §1 — in a throwaway worktree, driving its own `SqlConnectionsLoader` against that database.

  **What it does:** it never reaches the rows. The `Protected` sentinel is AEAD ciphertext too and is read first, so the legacy provider fails on it before a single row is touched. The client asks for a **master password the database does not have** and the user has therefore never set; refused one, it throws `Could not load SQL connections` and writes **nothing at all** to the notification panel. No version is named anywhere. So the feared outcome — plausible garbage decrypted out of AES-CBC and shown as empty passwords — cannot happen, because the sentinel gate is reached first. Four places in the repository asserted the wrong version of this and have been corrected rather than left: design.md, this file's §2.1 note, the CHANGELOG entry, and a comment in `SqlDatabaseVersionIntegrationTests`.

  **And it found a defect that undoes §1.** `ConnectionsService.LoadConnections` catches any exception from a database load and, if a local SQL connections cache exists, loads *that* instead — warning "Loading from local cache in read-only mode". **Nothing sets read-only.** `UsingDatabase` stays true, the saver's only read-only gate is the user's own `SQLReadOnly` setting, and the next save writes the stale cached tree back over the database under the legacy provider. For exactly the population §1 protects — people who have loaded from SQL before, and so have a cache — the refusal becomes "work from a stale copy, then overwrite the upgraded database with it". The refusal is correct and lands one level too low. Out of scope for this change, and now proposed as `refuse-writes-from-a-cached-fallback` — which should land soon after §1, because until it does §1's refusal never reaches a user who has a cache. That proposal carries a second finding from the same few lines: the cache is a full copy of every password in the store, written on every successful load, and for a database with no master password it is keyed with the published legacy constant.
- [x] 6.7 Manual: alter a `Password` value in the database directly and confirm the client reports a decryption failure rather than returning a wrong value. — **Found a real defect before it was ever run by hand** (see 5.1): the deserializer was returning the ciphertext as the password. Then, run against a real database — a byte flipped inside one stored ciphertext, loaded through the real `SqlConnectionsLoader` — it found a second one.

  The substance was right: the tampered connection loaded with an empty password rather than a wrong one, the other connection loaded intact, and the load did not abort. **But the message did not say which connection.** "A stored password in the SQL database could not be decrypted" is close to useless in a store with two hundred of them, and there is no second place to go and find out — this is the notification, not a summary of one. The row is in scope at the point of failure, so it now names the field and the connection: *"The Password stored for connection 'webserver' could not be decrypted..."*. `AnAlteredValueIsRefusedRatherThanUsed` asserts the name and the field appear, not merely that something was reported.

  Worth recording that the check as written would have passed on the old message. It asked for "a decryption failure rather than a wrong value", and that was already true. What made it useful was looking at what the user is actually left holding.
