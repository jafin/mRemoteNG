back with no machine protector, and the cause was that `build.ps1` produces a portable build.

## 2. Convert the compile-time sites

- [x] 2.1 `ChooseProvider` derives unconditionally from `LocalFileSettingsProvider`; `PortableSettingsInitializer` selects the provider at runtime. — **This was the one site that genuinely needed a compiler**, because it selected a base class. The initializer already ran before any setting was read and already wired one instance to every settings class, so the fix belongs in the one place that could always have made the choice. **The first version of it was wrong and shipped a regression — see 2.6.**
- [x] 2.6 **Regression, reported by the user and fixed: the update-settings prompt returned at every launch however it was answered.** 2.1 first pointed the installed edition at `LocalFileSettingsProvider`, which is what `ChooseProvider` had always compiled to when `PORTABLE` was undefined. That path had never executed in this application's history — every configuration defined the constant — and it persists nothing: no `user.config` is written and every setting returns to its default at the next start. Evidence at the time of diagnosis: no `user.config` anywhere since 10 August, `mRemoteNG.settings` last written the minute before the change, and `extApps.xml`/`pnlLayout.xml` still updating that morning, because those are written by explicit file writers rather than through the provider. **The fix is that both editions use `PortableSettingsProvider`**, which is misnamed: it is a file-based provider writing to `SettingsFileInfo.SettingsPath`, and *that* is what follows the edition. The edition already decided the location; making it also decide the provider added a second mechanism that had never worked. Pinned by `SettingsProviderSelectionTests`, confirmed non-vacuous — restoring the broken selection fails two of its three tests.
- [x] 2.7 **`UserSettingsFilePath` reported a file nothing writes.** Found while writing 4.4's documentation of where settings live. 2.6 put both editions on `PortableSettingsProvider`, which writes `<SettingsPath>\<exe>.settings`; this property still returned the framework's `user.config` for the installed edition. Every diagnostic that names the settings file — the startup log, the "Loading settings from" message, the debug report — therefore pointed at a path that could not exist and reported "file does not exist — using defaults" while settings were persisting correctly beside it. That is the same class of misdirection this whole change exists to remove, and it would have cost the next person the session it cost this one. Now one expression for both editions, since `SettingsPath` is already the edition-aware part. Pinned by `SettingsProviderSelectionTests.TheReportedSettingsFileIsTheOneTheProviderWrites` for both editions.
- [x] 2.2 `DockPanelLayoutLoader` and `ExternalAppsLoader` — the pre-`Settings`-folder path becomes null for portable rather than absent from the compilation.
- [x] 2.3 `IeBrowserEmulation` — both cleanup methods compile always; `Unregister` returns early when not portable.
- [x] 2.4 `FrmAbout` — `[Conditional("PORTABLE")]` becomes a runtime check.
- [x] 2.5 Remove `PORTABLE` from `Debug|*` and `Release|*` in the csproj, and then — under 4.3 — from every remaining configuration. Verified per configuration with `-getProperty:DefineConstants`: `Release` is `TRACE;RELEASE`, `Release Portable` is `TRACE;RELEASE_PORTABLE`, `Release Self-Contained` is `SELF_CONTAINED;RELEASE_SELF_CONTAINED`. The constant is now defined by nothing and referenced by no code.

## 4. Packaging

- [x] 4.1 `build.ps1 -Portable` writes `portable.flag` into its output. — Done, with permission granted for that file. It also **stops passing `-p:DefineConstants=PORTABLE`**, which was doing quiet harm beyond the edition switch: that property *replaces* the constant list rather than adding to it, so every portable build was compiled without `TRACE` and `RELEASE`. The marker's text says what it is and that deleting it makes the same binaries the installed edition — contents are never read, so it costs nothing to be useful to whoever opens it. Verified: `Wrote portable.flag marker`, and the file sits beside `mRemoteNG.exe` in `bin\x64\Portable\`.
- [x] 4.2 The self-contained release asset is advertised as portable and must actually be. — `Build_mR-NB.yml` step 09 writes `portable.flag` into the package for the self-contained leg only, matching the release notes' "**Self-Contained** - Portable, no installation required". It had been portable only by accident of the compile constant; without this it would have shipped as the installed edition, writing settings to `%APPDATA%` and giving connection files a machine-bound protector that cannot follow it to another machine. **Written at packaging time, not into the build output**: the framework-dependent leg packages `bin\<platform>\Release`, and step 09a harvests that same folder into the MSI, so a marker placed there would ship inside the installer and make an installed application behave as a portable one. The `publish` subfolder belongs to this leg alone.
- [x] 4.2b Assert the edition of each package rather than assuming it. — The post-zip check now tests both directions: the self-contained zip must carry the marker, the framework-dependent zip must not. Getting this wrong is silent at build time and reaches users as settings in the wrong place or a password prompt on every open, which is precisely how every artefact became the portable edition unnoticed. **Both guards were rehearsed against real archives and confirmed to fire**, since a guard that cannot fail is decoration.
- [x] 4.2a The MSI must not carry the marker. — Correct by construction: step 09a harvests `mRemoteNG\bin\x64\Release`, which has no marker in it.
- [x] 4.3 Remove `PORTABLE` from the remaining configurations and delete the `#if PORTABLE` branch in `PortableEdition.Detect`. — Done, and it did not need 4.2 after all: **CI never uses `build.ps1` and never builds those configurations.** Both matrix legs of `Build_mR-NB.yml` run plain `Configuration=Release`, so `Release Portable`, `Debug Portable` and `Release Self-Contained` were dead as far as any artefact is concerned. The constant is now defined by nothing and the marker is the only answer. Verified per configuration with `-getProperty:DefineConstants`.
- [x] 4.4 Release note for existing users (the one packaging item left): a portable installation that upgrades by copying only the executable, rather than extracting the zip, will come up as the installed edition and appear to have lost its settings. The zip is the supported upgrade path and the marker is why. — Written in four places, because the audience is in four places: the stable release body (`Build_mR-NB.yml`), the nightly release body (`nightly.yml`), `CHANGELOG.md`, and a new user-facing page, `docs-website/docs/portable-edition.md`. Each says the same three things: nothing was deleted, the files are still beside the executable, and an empty `portable.flag` brings them back.
  - **The nightly note is the one that matters most, and writing it turned up that the nightly body was wrong.** It advertised its ZIP as "Portable — extract and run", which was true only through the compile constant. That ZIP is packaged from `bin\x64\Release` — the same folder harvested into the MSI — so under 4.2's reasoning it cannot carry the marker, and every existing nightly user's next upgrade moves their settings to `%APPDATA%`. The row now says installed edition and the note tells them how to opt back in. Making the nightly ZIP portable instead was not taken: it would put a marker in the MSI's harvest folder, which is precisely the failure 4.2 was written to prevent.
  - Two corrections to `docs-website/docs/troubleshooting.md` fell out of writing the page, both pre-existing: the installed log path is `%LOCALAPPDATA%`, not `%APPDATA%`, and portable settings live in the `Settings` subfolder rather than beside the executable.
