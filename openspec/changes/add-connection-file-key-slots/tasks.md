# Tasks

Depends on `replace-default-connection-file-key`, which introduces the per-file key and the two
protectors. There is nothing to add slots to before it lands, and its task 5.5 — no machine protector
on a file outside the user profile — is what this change exists to reverse for the shared case.

Do not start before it ships. Landing slots first would produce files whose `KeyProtectorMachine`
holds a list that the build shipped alongside them reads as a single blob.

## 1. Slots in the format

- [x] 1.1 Make `KeyProtectorMachine` a `|`-separated list of wrapped keys. A single entry is the existing form, so a file written by the preceding change is a one-element list and needs no migration and no version flag on the attribute. **Not a space:** `Convert.FromBase64String` ignores whitespace, so a space-separated list read by a build expecting one blob would sometimes concatenate silently instead of failing, depending on whether the entries carry `=` padding. `|` is outside the base64 alphabet and is not whitespace, so an older build fails the same way every time.
- [x] 1.2 Unwrap by trying every slot in turn and accepting the first whose key **decrypts the root sentinel** — not merely the first that unwraps. `ProtectedData.Unprotect` succeeding proves the blob was written by this account, not that it belongs to this file: a slot copied from another file the same user owns unwraps perfectly and yields the wrong key, and the store then opens onto contents that do not decrypt with nothing reported. Continue the search past a slot that unwrapped but did not authenticate.
- [x] 1.3 Remember which slot succeeded for the session, next to the recovery password `replace-default-connection-file-key` task 5.6 already caches, so the search happens once per run rather than once per read. — `MachineSlotSession`, beside the recovery password's. Deliberately **not** cleared by the autolock, unlike that one: a wrapped key is public and unwrapping it still needs the account already signed in, so remembering it defeats nothing the lock is for.
- [x] 1.4 Refuse a file whose slot list is empty but whose attribute is present, rather than reading it as "no machine protector". An attribute that is there and says nothing is a file something went wrong with, not a portable one. — Note the distinction this rests on: absent means absent, and the deserializer passes null for a missing attribute rather than empty, so the two cannot be confused. One existing test asserted the old reading and was rewritten in place rather than deleted.
- [x] 1.5 Bound the slot count and refuse an over-long list **before** trying any slot. The slots are tried in turn, so without a bound a file declaring a hundred thousand of them takes minutes to refuse to open.
- [x] 1.6 Tests: a one-element list is exactly what the preceding change writes, and an absent attribute still means no machine protector; N slots each unwrap the same key; a foreign slot among valid ones does not prevent the valid one being found; a slot that unwraps to a key from a different file is rejected rather than accepted; an empty list is refused; an over-long list is refused without attempting a slot; a multi-slot value read by a single-slot reader fails deterministically rather than concatenating.

## 2. Earning a slot

- [x] 2.1 When the store was opened by the recovery password and the current user has no slot, add one **on the next save** — never on open. Rewriting a file that was only read is what `replace-default-connection-file-key` decided against, and on a shared file it would make every open a write to a file other people have open. — `ConnectionFileKeyProtection.HasSlotForThisAccount`, set by `Create` when it writes one and by `Unwrap` when a slot opens the file. "Does the file have a machine protector" is the wrong question once slots exist: a shared file has several and none of them is yours. False is the safe direction — being wrong that way costs a duplicate slot, being wrong the other way leaves a member prompted for ever.
- [x] 2.2 Do not add a slot in the portable edition, whatever the format allows. There is no account worth binding to on a machine the build was carried to, and a slot per machine visited grows without bound and serves nobody.
- [x] 2.3 Reverse `replace-default-connection-file-key` task 5.5 for the shared case: a file outside the user profile may now carry machine protectors. Leave the portable gate alone — that one is about the edition, not the location. Record in the code that the two rules had a single implementation and no longer do. — `MachineProtectorPolicy.ShouldWriteMachineProtector` now answers only the edition question. `IsInsideUserProfile` stays, because "is this file likely shared?" is still real — it decides what the user is told before choosing a recovery password — but it no longer decides what is written. Both the rule and the reason are recorded there.
- [x] 2.4 Tests: a second account opening a shared file is prompted once, then not again after a save; a read-only member is prompted every time and the file is not written; the portable edition adds no slot. — Including an end-to-end one through the saver: a store carrying another account's slot, opened here with the recovery password, gains a second slot on save while the first is left untouched, and then opens silently. That is as close as one process can get to two Windows accounts. Also pinned: a member who already has a slot does not collect another on every save, which would otherwise grow a daily-used file to the bound.

The user-visible half of §2 is documented: the shared-file section of
`docs-website/docs/connection-file-protection.md` described the old behaviour — everyone but one
person prompted on every open, for ever — and now describes earning an unlock on save, including
what that costs a member who only reads. `RecoveryPasswordSharedStore`, which the user is shown
*before* choosing a recovery password, said the same thing and now says "once each" rather than
"on every open".

## 3. Rekey

- [x] 3.1 Offer a rekey: new file key, new recovery password, contents re-encrypted, every slot dropped and the current user's written. This is the removal operation — deleting a slot is not offered, because it does not remove access from someone who knows the recovery password and has had the file. — `ConnectionFileRekey.Apply` replaces the key and the protection; the contents are re-encrypted by the save that follows, because the saver encrypts with whatever key the root carries. Two fields rather than a second implementation of writing the file. Offered at **File → Rekey Connection File...**, never implied by anything else.
- [x] 3.2 Say in the confirmation what a rekey does and does not do: copies taken before it still open, up to the point they were taken. Every rekey of every system has this property and a user who is not told it will assume otherwise. — Three paragraphs in the order the user needs to answer: what it changes, what it cannot reach, what is kept. The middle one is the one they will not think of themselves, and it goes further than the task asked — a copy taken beforehand still opens, so the passwords in the file should be treated as known to whoever took it and changed on the systems themselves. Assembled outside the dialog so a test can assert what a security warning says without needing a window.
- [x] 3.3 Take a backup before a rekey, through the existing `FileBackupCreator`, and confirm the backup is of the pre-rekey file. A rekey that half-completes on a share is the one path here that can lose a store. — Through the existing `FileBackupCreator`, before `Apply` is called and therefore of the pre-rekey bytes. The confirmation says the backup still opens with the old recovery password, because a backup that silently outlives a revocation is worse than no backup. Ordering is by inspection here — the prompt runs on `Runtime` statics — and by manual check 5.5, which opens that backup with the old password.
- [x] 3.4 A rekey in the portable edition writes no slot, like every other portable write. Rekeying is about the key and the password; it is not an occasion to start binding to a machine the build was carried to.
- [x] 3.5 Tests: after a rekey the old recovery password opens nothing; the new one opens everything; a pre-rekey backup still opens with the old password; the contents survive the round trip unchanged; a portable rekey writes zero slots. — Nine, including the two that matter most: the old password opens nothing afterwards, and **the key itself is replaced rather than re-wrapped**. A rekey that kept the key would leave every copy openable by anyone holding the old one, which is the whole thing it exists to stop. Also that a colleague meets the new password once and is re-slotted on their next save, that a rekey with no new password is refused and leaves the store untouched, and that the confirmation carries all three paragraphs.

## 4. Concurrency

- [x] 4.1 Record a key generation in a root attribute, changed only by a rekey, and **refuse a save whose generation differs from the one this session read**. Without it a member who had the file open before a rekey writes the contents back under the old key and the old recovery password on their next save, silently reinstating the access the rekey removed — to a user who never knew a rekey happened. Refusing a save is unpleasant; only one of the two outcomes is recoverable by the person it happens to. — `KeyGeneration`, a 128-bit random token written in the clear beside the protectors and set by `ConnectionFileKeyProtection.Create` alone, which means by hardening and by a rekey. **A token rather than a counter:** two rekeys from two sessions both bump a counter to the same number, so a counter can say "unchanged" about two different keys, which is the one answer this must never give. Compared against `RootNodeInfo.KeyGenerationSeen` — what the file said when this session read it — rather than against the protection's own generation, because those differ for exactly as long as a rekey is unsaved and that is the one save that must go through.
- [x] 4.2 Leave ordinary saves last-writer-wins. Nothing about them is a security boundary and they are already last-writer-wins today; the generation check is for the rekey path alone. — Which is what makes the null-propagation rule load-bearing: a file written before generations existed does **not** acquire one on an ordinary save. Filling it in would hand every other session holding that file a token they had never seen, and their next ordinary save would be refused for a rekey that never happened. Adding a slot and changing the recovery password both carry the generation over for the same reason — same key, so nobody's copy has been invalidated.
- [x] 4.3 Confirm by inspection that a lost slot costs one prompt — a member whose slot was overwritten by another's save supplies the recovery password and rewrites it on their next save. Note that this is repaired *by the member*, not on its own: a member who never saves is never repaired. No locking. Record the reasoning where the slot is written, not only here. — Recorded in `WithMachineProtector`, which is where a reader meets the additive write. Confirmed: the later save serializes the slot list its own session holds, so a slot earned between the two reads is dropped; the member is asked for the recovery password on their next open and slotted again on their next save.
- [x] 4.4 Confirm a concurrent save cannot produce a file with a valid slot list and contents keyed to a different file key. This is the one race that would be destructive rather than annoying. — It cannot. The protectors and the contents come from one serialization of one root node, so they always describe the same key, and `FileDataProvider.Save` writes a temporary file and replaces the original in one step — a reader sees one writer's whole file or the other's, never halves of both. Recorded on `XmlConnectionsSaver.Save`.
- [x] 4.5 Tests: two protection objects derived from the same file, saved in sequence, leave a file both can still open; a save held from before a rekey is refused and does not restore the old protectors; a save from before an ordinary save is not refused. — Nine, in `ConnectionFileGenerationTests`, all through the real saver and deserializer against a file on disk, with the second session played by a second model loaded from the same file before the rekey. Beyond the three asked for: the refused save leaves the file byte-identical and the retired password still retired; the session that rekeyed can save twice, which is the check that fails if the comparison is made against the wrong generation; and both halves of the pre-generation case — such a file saves normally and stays without one, but once rekeyed it refuses the stale save all the same.

## 5. Verification

- [x] 5.1 Full build; zero new analyzer warnings. — Clean. Two warnings §3 had introduced in `ConnectionFileRekeyPrompt` (a nullable connection file name) were fixed here rather than left: the name is now refused explicitly, since the menu item is enabled only with a file loaded and a null there is an impossible state rather than a user error.
- [x] 5.2 Full test suite; zero failures, no `[Ignore]`. — 4206 passed, 0 failed. One existing test needed the save-refusal checks reordered rather than changing: `ARefusedStoreIsNotWrittenOver` saves a model with no root node, which is a legitimate way to assert that an unreadable *storage format* stops a write before anything else is considered. The format check now runs before the root node is looked up and the generation check after it, which is the correct order anyway — only one of the two needs the store.
- [x] 5.3 `openspec validate add-connection-file-key-slots --strict`.

Documented with §3 and §4 together, since a user meets them as one thing: `connection-file-protection.md`
gains **Removing someone's access** — what a rekey does, what it cannot reach, and what to do about the
copies it cannot reach — and the refused-save message, which is the one place in this change a user is
stopped and needs to know their unsaved work is safe. The recovery-password warning said there was no
way to change it, which a rekey now is. The CHANGELOG entry for the preceding change said a file outside
the user profile carries no automatic unlock; §2 reversed that, and leaving both claims in one release's
notes would have been worse than either.
- [ ] 5.4 Manual: two Windows accounts, one connection file outside both profiles. Migrate from the first; open from the second with the recovery password; save; confirm the second opens silently thereafter **and the first still does**. The second half is the point — this change is worthless if a slot serves one member at a time.
- [ ] 5.5 Manual: rekey from one account, confirm the other is prompted for the new password once and then silent, and that a backup taken before the rekey still opens with the old one.
- [ ] 5.6 Manual: open a file written by `replace-default-connection-file-key` with no slots added, and confirm it opens unchanged and gains a slot only when saved.
- [ ] 5.7 Manual: rekey from one account **while the second has the file open**, then save from the second. It must be refused. This is the path where a race stops being an annoyance and becomes a silent un-revocation, and it is worth doing by hand because a test can only simulate the two sessions.
