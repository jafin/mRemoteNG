## 7. Agent precedence and temp-file removal

- [x] 7.1 ~~Implement precedence in the resolver.~~ **Done 2026-08-08, but as ADDITIVE rather than precedence — D5 revised.** The resolver now takes an optional `ISshAgentProvider` and populates `ResolvedSshCredential.AgentIdentities` when `options.ConsultAgent` is set. Agent identities are offered *alongside* the configured key path, provider key material and discovered default — not instead of them. Reason: an agent holding *a* key says nothing about whether it holds *this connection's* key, so suppressing a vault key because an unrelated identity is loaded would break authentication intermittently. SSH auth offers candidate keys in turn and the server chooses; `PrivateKeyAuthenticationMethod` takes an array for exactly this reason. 6 new tests.
- [x] 7.2 ~~When the key source is an agent identity, skip the temp-file write.~~ **DEFERRED 2026-08-08 (maintainer decision: option C).** Filed as its own change, `add-ssh-agent-key-injection`, with the full analysis in its proposal. Deferred rather than dropped: the hazard is real but pre-existing, agent injection is a distinct mechanism with its own failure modes (key-format parsing, agent availability, key lifetime), and bundling it here would attach that risk to an otherwise well-tested refactor. The `ssh-agent-authentication` spec was amended to record the guarded temporary file as current behaviour and to name the deferral, so the contract matches what is built. Original analysis: Three independent reasons: (a) with additive semantics there is no "the key source is an agent identity" state to branch on; (b) the backend that writes the temp file is PuTTY, and PuTTY never consults `ISshAgentProvider` — `ForPutty` sets `ConsultAgent: false` because it talks to Pageant natively — so the condition could never fire; (c) the temp file is only written when a *vault* supplies a key, and a vault-supplied key is by definition not already in the agent. **The hazard is still removable by a different mechanism**: parse the vault key into an SSH.NET `PrivateKeyFile` and inject it into Pageant via `SshAgent.AddIdentity(key, lifetime, confirm)`, so it lives in agent memory with an expiry and never reaches disk. That is new work, not a skipped write — `PrivateKeyFile` parses OpenSSH/PEM but not `.ppk`, the vault's format is not guaranteed, Pageant must be running, and a temp-file fallback is still needed. See design.md D5.
- [x] 7.3 Test the temp-file behaviour. **Deferred with 7.2** to `add-ssh-agent-key-injection`. The behaviour that remains in this change — provider key material materialised to a temporary file, then zero-filled and deleted — is unchanged from before the refactor and is covered by the existing characterization tests (`ConfiguredPrivateKeyPathIsPassedWithIdentityFlag` and the resolver's `MaterialisedKeyMaterialSuppressesDiscovery`).
- [ ] 7.4 ~~Confirm the PuTTY adapter emits no `-i` for provider key material when an agent identity is in play.~~ **Not applicable** — follows from 7.2(b): PuTTY never sees agent identities, so this state cannot arise. If 7.2 adopts agent injection, the adapter correctly emits no `-i` because there is no temp path to emit, which is already the existing behaviour rather than a new branch.
